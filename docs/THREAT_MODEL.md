# 脅威モデル（Silent Sync Lab）

EXPERIMENTAL — NOT FOR MAINNET OR REAL FUNDS. 未監査の実験コードであり、本番資産向けの安全性は一切主張しない。

この文書は「何を守ろうとしていて、何を守れないか」を、実装とテストで確かめた範囲で書く。
推測で書いた箇所は `UNVERIFIED` と明記する。

## 1. 対象と前提

| 項目 | 内容 |
|---|---|
| 守る対象 | (a) scan 秘密鍵、(b) 出力ごとの tweak（spend 鍵と合わせると支出鍵になる）、(c) 受信履歴（どの出力が自分宛てか）、(d) 検出結果の正しさ（見逃し・誤検出・重複がないこと） |
| 扱わないもの | spend 秘密鍵（この実験は保持しない。検出に使うのは spend **公開**鍵のみ）、送金・署名、残高、実資金、mainnet |
| 鍵 | BIP352 公式テストベクトルの**公開された**テスト鍵のみ。利用者のシードは取り込まない。したがって現状の (a)(b)(c) は秘密ではないが、コードは秘密として扱う（ログ・JSON・`Debug`・DB・エラーに出さない） |
| ネットワーク | regtest / signet。mainnet は型・パーサ・serde・genesis hash・チェーン名の各層で拒否 |
| 接続先 | この機械のループバック（`http://127.x.y.z:<port>` の IPv4 リテラル）だけ。名前解決・TLS・プロキシ・リダイレクト追従は無い |

## 2. 登場するものと、それぞれへの信頼

| 相手 | 何を受け取るか | 信頼していること | 信頼していないこと |
|---|---|---|---|
| 上流ライブラリ `bdk_sp`（rev 固定）と暗号スタック | BIP352 の計算 | 計算の正しさ（公式ベクトル 29 件で確認。逸脱 2 点は `silent-sync` で補正: RESEARCH U-1, U-2） | panic しないこと（`catch_unwind` で封じ込め） |
| 自分の Bitcoin Core（REST） | ブロック、spent outputs、ヘッダ | **spent outputs が正しいこと**（何にもコミットされておらず検査できない。FAULT_INJECTION F05）。先端を隠していないこと（F06） | ブロックの中身（ヘッダ鎖・PoW・merkle root・witness commitment を検査）、チェーンの申告（genesis から連結を検査） |
| tweak インデックスサーバ（BlindBit Oracle） | tx ごとの tweak と Taproot 出力 | 何も（ブロックの同一性は自分のノードのヘッダで確認する） | 完全性・正しさ。**省略・改変・捏造を単独では検出できない**（I01〜I06） |
| ローカルのストア（SQLite ファイル） | チェックポイント、検出結果 | 自分が書いた内容がそのまま残っていること（開くときに連続性・連結・バインディングを検査） | 整合性の暗号的保護は無い。ファイルを書き換えられる攻撃者には無力 |
| この機械の他のプロセス・利用者 | — | — | ループバックのポートを奪って偽サーバを立てることは防げない（下記 4.4） |

## 3. プライバシー

### 3.1 外に出ていくもの

- ループバックの HTTP リクエストのパスだけ: Core へは `/rest/chaininfo.json`、`/rest/headers/<hash>.bin`、`/rest/block/<hash>.bin`、`/rest/spenttxouts/<hash>.bin`、`/rest/blockhashbyheight/<h>.hex`。Oracle へは `/info` と `/full-block/<height>`。
  **鍵・tweak・アドレス・ラベルは送らない**（テスト: 偽サーバが受け取ったリクエストのパスが上記の形だけであること。`oracle_fake.rs`、`core_rest_fake.rs`）。リクエストはパスのみの GET で、本文も独自ヘッダも付けない。
- スキャンは常にローカルで行う。サーバに「この出力は自分のものか」を尋ねる経路は無い。

### 3.2 それでも見えるもの

- **要求したブロック範囲と時刻**。birthday から先端までを順に取得するので、サーバは「このクライアントの関心がどの高さから始まるか」を知る。
- リモートのサーバを使う場合は、これに IP アドレスが加わる。**この実験はリモート接続を実装していない**（ループバック以外の URL は拒否）。
  リモートの tweak サーバを使う構成は、scan 鍵を渡さなくても匿名性を保証しない（設計書 §5.4）。別モードとして明示的な同意の下でのみ扱うべきもので、未実装（DECISIONS O-015）。
- 全ブロックを取得するフルブロック型と、全 tweak を取得するインデックス型は、どちらも「特定の tx だけを取りに行く」ことをしないので、**取得パターンから自分の tx は絞り込めない**（範囲内の全ブロックを一様に要求する）。これは設計上の性質で、範囲を絞る最適化（フィルタ等）を入れると失われる。

### 3.3 ローカルに残るもの

- ストアには受信履歴（txid・vout・金額・ラベル・高さ）と公開のウォレット識別子が入る。鍵・tweak は入らない（ファイルのバイト列を検査するテストあり）。ファイルは 0600。
  暗号化はしていない。ディスクを読める者は受信履歴を読める。
- ベンチマーク結果には txid・ウォレット識別子・パス・URL を含めない（テストあり）。失敗した run はエラーの分類だけを記録し、文面は記録しない。ブロックハッシュと、利用者が `--note` に書いた文字列は含む。
- ログ・エラーメッセージ: 外部由来の文字列は制御文字を除去し長さを制限して出す。認証情報を含み得る URL は表示しない。

## 4. 完全性（検出結果の正しさ）

詳細な注入結果は `docs/FAULT_INJECTION.md`。要点だけ再掲する。

### 4.1 単独で検出できる（fail-closed）

ノードが示すヘッダ鎖と食い違うブロック内容、witness の除去、別ネットワーク・別の genesis のデータ、ヘッダと一致しないインデックス、
順序違い・重複・欠落・部分応答、応答なし・停止、遅れているソース、同期中のチェーン変更。
いずれも範囲全体を失敗にし、「同期済み」と報告しない。途中まで進んでいた場合は、どこまで変更したかを報告する。

### 4.2 単独では検出できない

| 何が起きるか | どのバックエンドで | 緩和 |
|---|---|---|
| 入金の見逃し（サーバが項目を省略・改変） | tweak インデックス | 自分のノードとの突き合わせ（`verify`）。それ以外に手段は無い |
| **誤った金額での検出** | tweak インデックス | 同上 |
| **存在しない入金の検出**（捏造） | tweak インデックス | 同上。検出結果に証拠種別 `tweak_index` を付けて区別している |
| 入金の見逃し（範囲より前の prevout を偽る） | フルブロック | 無し。自分のノードを信用する前提 |
| 最新ブロックが見えない（先端を隠す） | すべて | 無し。別の情報源で先端を知るしかない |
| **一貫した別チェーン**（genesis から連結した偽のチェーンをヘッダごと出す）。入金の見逃しと、存在しない入金の検出の両方が起きる | フルブロック（接続先が自分のノードでない場合） | regtest / signet では PoW が意味を持たず、防げない。接続先が本当に自分のノードであることが前提（4.4） |
| スキャン時だけの嘘（後の問い合わせには正直に答える） | すべて | `verify` では分からない（再度問い合わせて比べるだけ）。保存済みの結果を自分のノードと比べる `audit` で分かる（D-042）。監査するまでは気付けない |

**tweak インデックス由来の検出を、支払いの確認として使ってはならない。** この実験の表示は `detected_received_outputs` であり、残高でも着金確認でもない。

### 4.3 突き合わせの限界

2 つのソースの一致は、参照側が正直で完全な場合にのみ意味がある。自分で運用していない複数サーバの一致は、独立した正しさの証明ではない（同じ上流データ・同じ実装・同じ運用者であり得る）。

### 4.4 ローカルの攻撃者

- ループバックの別プロセスが、ノードや Oracle のポートを先に取って偽の応答を返すことは防げない。フルブロック型でも、偽のチェーンをヘッダごと一貫して出されれば 4.1 の検査はすべて通る（FAULT_INJECTION F12）。**フルブロック型の保証は、接続先が自分のノードである場合に限られる。** 接続先の認証（cookie 認証つきの RPC など）は使っていない。
- ストアのファイルを書き換えられる攻撃者は、検出結果を自由に改変できる（開くときの検査は破損の検出であって改ざん防止ではない）。
- 鍵は現状ソースコードに埋め込まれた公開テスト鍵で、保護の仕組みは無い。実際の鍵を扱うには OS のキーストア等が必要で、未設計（Phase 6 の判断材料）。

### 4.5 可用性

- 応答 1 件は 64 MiB、待ち時間は 30 秒で打ち切る。ブロックあたりの tx 数にも上限がある。
- reorg の巻き戻しには上限がある（既定 100 ブロック。DECISIONS D-041、D-044）。**上限は 1 回の同期呼び出しに対するもの**。それより深く書き換えて見せるソースは拒否され、ストアは変わらない。チェックポイントより短い競合チェーンにも追随しない（成功した呼び出しがストアを低くすることは無い）。
  - 残る限界: 巻き戻しの直後に毎回失敗して見せるソースは、呼び出しごとに上限ぶんまでストアを下げられる。巻き戻しは毎回報告されるので、繰り返される巻き戻しはソースの異常として扱うこと（O-019）。利用者が上限を外した場合（`none`）は、1 回で保存分すべてを巻き戻させることができる。
- 再スキャン（`lab add-label` / `lab rescan`）の途中経過はストアの隣の `<store>.rescan` に置き、完了後にストアと差し替える。このファイルは「通常ファイル・ストアと同じ所有者・他のユーザーが読み書きできない」場合にだけ使う（リンクや他人のファイルは拒否）。同じ所有者が書けるファイルである以上、ストア本体と同じく、書き換えられれば中身はそのまま採用される（改ざん防止ではない）。ストアは共有ディレクトリに置かないこと。
- 2 プロセスが同じストアに同時に書くことはサポートしない。壊れないこと（ロック待ち・不変条件による拒否）だけを保証する。

## 4.6 ウォレット（`silent-wallet`、`wallet-cli`。regtest / signet のみ）

受信専用の部分と違い、ここは spend 秘密鍵を扱い、tx に署名して送る。扱うのは無価値のコインだけで、mainnet は型として表現できない。

**守っていること**

- **鍵とシード**: 起動のたびに環境変数から受け取り、ファイルに書かない・表示しない・エラーに含めない。CLI に鍵を作る・見せるコマンドは無い。
- **出力ごとの tweak**: 保存しない。支出するときに、その出力のブロックを自分のノードから取り直し、スキャンし直して得る。ブロック・tx・出力・金額・ラベルが検出時と一致しなければ使わない。署名が済めば捨てる。
- **署名の前後の検査**（`send.rs`）: 導出した鍵がその入力の出力スクリプトの鍵と一致すること／署名が検証を通ること／手数料が「入力 − 出力」で、上限以内であること／**完成した tx を自分のスキャナにかけて、お釣りが見つかること**（見つからなければ tx を返さない。お釣りを見失う鍵には送らない）。
- **送信**: 内容を表示し、`SEND` と入力されたときだけ送る。省略する手段は無い。接続先はループバックのみ。認証情報（cookie）はファイルから読み、表示・保存しない。
- **「未使用」の意味**: フルブロックで検出し、使用済みの記録が無い出力だけ。インデックス由来の検出は別枠で、合計しない。

**守れないこと・前提**

- 環境変数は、同じ利用者の他のプロセスから読める場合がある（`/proc/<pid>/environ` など）。鍵の保管は未設計で、実際に価値のある鍵を扱える状態ではない。
- 未承認の tx（mempool）は見ない。自分が送った tx は手元の記録（`<store>.pending.json`）で使用中として扱うが、**外から届いた未承認の入金は見えず、他のウォレットが同じ鍵で送った tx も分からない**。
- 送信の直後にプロセスが落ちると、送った tx が手元の記録に残らないことがある。その場合、ブロックに入るまで入力が未使用に見える（もう一度送ろうとしても、ノードが二重使用として拒否する）。
- 自分のノードが嘘をつけば（F12）、存在しない入金を未使用として見せられる。送金は本物のネットワークで拒否されるので資金は失わないが、表示は誤る。監査（`audit`）は別のフルノードがあって初めて意味を持つ。
- コイン選択は「古い順」で、プライバシーへの配慮（入力の結び付き、お釣りの位置）はしていない。お釣りは常に最後の出力。
- 署名に補助乱数を使っていない（`sign_schnorr_no_aux_rand`。決定的で、同じ tx には同じ署名になる）。サイドチャネルへの追加の防御が無いという意味で、ハードウェアを共有しない前提。
- 3 つの自己検査（鍵の一致、署名の検証、お釣りの検出）は、ライブラリが正しい限り失敗しないため、**失敗する側のテストが無い**（無効化チェックの対象外）。

## 5. 上流・依存

- 暗号スタックは上流のロックファイルと同じバージョンに固定（DECISIONS D-004）。`cargo update` を無指定で実行しない。
- 上流の挙動を補正している箇所（K_max、SegWit v>1、panic の封じ込め、tweak インデックスからのスキャン）は**人間レビュー対象**（DECISIONS D-005、D-006、D-030）。
- 上流 `bdk_sp` は未監査・実験的と自称している。この実験もそれを引き継ぐ。
- テスト用のバイナリ（Bitcoin Core、BlindBit Oracle）はリポジトリに含めず、取得スクリプトがハッシュ（Core は署名も）を検査する。

## 6. 確認できていないこと（UNVERIFIED）

- 実際の signet での動作（カスタム signet を含む）。コード上は genesis hash で区別するが、実ノードでは未確認。
- 非 Linux 環境。ファイル権限（0600）と CPU 時間の計測は Unix / Linux 前提。
- BlindBit Oracle の gRPC インターフェース（HTTP JSON のみ実装。上流では HTTP が deprecated: O-014）。
- 長時間・大規模（数十万ブロック）の同期。計測したのは最大 1000 ブロック。
