# ウォレット段階の設計案（承認前）

EXPERIMENTAL — NOT FOR MAINNET OR REAL FUNDS.

**状態: 提案。コードは 1 行も書いていない。** この文書は、所有者の判断をもらうためのもの。
ウォレット段階は「資金利用を可能にする変更」「秘密情報の扱いの変更」を含み、CLAUDE.md により人間レビューが必須。
承認された項目だけを、段階ごとに実装する。

- 前提となる決定: Phase 6 で「まず SDK を完成させ、その後それを使って新しいサイレントペイメントのウォレットを作りながら磨く」（`docs/PROGRESS.md`）。
- 上流の確認: `bdk_sp` rev `bb373e566fa2`（このリポジトリが固定しているもの）。確認したファイルは §7。

## 1. 目的

1. **SDK（`silent-sync` / `silent-sync-sqlite`）を、本物の利用者として使ってみる。** 使いにくい API、足りない機能、文書の不足を、作りながら見つけて直す。
2. その結果として、**regtest / signet で動く最小のウォレット**ができる: 受け取る → 使える分を知る → 送る。
3. mainnet と実資金は対象外のまま。`Network` に mainnet を足さない（規約 1 は変えない）。

「製品を作る」ことは目的にしない。UI の作り込みは最後の段階で、形（デスクトップ／CLI のまま）もそこで決める。

## 2. いまの規約のうち、変える必要があるもの

受信専用の実験として決めた規約のいくつかは、ウォレットでは守れない。**どこを、どの範囲で緩めるか**が最初の判断になる。

| 規約 | いま | ウォレットに必要なこと | 提案 |
|---|---|---|---|
| 1. mainnet・実資金 | 不可 | — | **変えない**。regtest と signet のみ。mainnet は型として表現できないまま |
| 2. 独自の暗号を書かない | EC 演算・ハッシュ・マッチングは上流を呼ぶ | 支出鍵 = spend 秘密鍵 + 出力ごとの tweak、署名、送金先の出力の計算 | **変えない**。すべて上流（`bdk_sp` と、それが再エクスポートする `bitcoin` / `secp256k1`）の関数を呼ぶ。自前の式は書かない。呼び出す箇所は 1 つのモジュールにまとめ、人間レビューの対象として明示する |
| 3. 秘密を出さない | scan 秘密鍵・tweak・シードを出力しない。リポジトリに新しい秘密鍵を置かない | **spend 秘密鍵を扱う**。出力ごとの tweak をウォレットに渡す | 「出力・ログ・`Debug`・panic・コミットに書かない」は**変えない**。変えるのは「tweak を公開 API から渡さない」（D-039）で、§4.2 の形に限って渡す |
| 5. 検出は残高ではない | 「残高」「利用可能」という語を使わない | 使用済みかどうかを追跡し、使える分を示す | **根拠つきで解禁**。§4.1。フルブロック型で使用済みを確認できた範囲だけを「未使用」と呼ぶ。インデックス由来の検出は合計に入れない |
| 6. 送金・署名を作らない | テスト専用クレートだけ | 送金と署名 | **新しいクレートに限って解禁**。`silent-sync`（同期コア）と `lab-cli` は受信専用のまま。§3 |
| 9. 製品形態を決め打ちしない | Phase 6 まで | — | 形（UI）は最後の段階で決める |

## 3. 構成の案

```
crates/silent-sync/          同期コア（変更は最小限。既定の機能は受信専用のまま）
crates/silent-sync-sqlite/   ストア
crates/lab-cli/              受信専用の実験 CLI（そのまま）
crates/silent-wallet/        【新規】ウォレットのライブラリ: 使用済みの追跡、コイン選択、送金 tx の組み立て、署名
crates/wallet-cli/           【新規】ウォレットの CLI（バイナリ）。UI を作るまでの操作手段
```

- 依存方向: `wallet-cli → silent-wallet → silent-sync, silent-sync-sqlite`。逆向きの依存は作らない。
- 送金・署名のコードは `silent-wallet` だけに置く。`silent-sync` に「署名」「送金」という語が現れないことを、いまの検査（既定 feature で届かないことの検査）と同じやり方で検査する。
- 上流には実験的なウォレット実装（`bdk_sp_wallet`）がある。**これをそのまま使う案は推奨しない**（§7）。理由: 同期・保存を上流の仕組み（`bdk_chain`）で行うので、私たちの SDK を試すという目的に合わない。本番経路に `unwrap` / `expect("will fix later")` / `unimplemented!` が残っている。使うのは、その下の部品（送金先の出力の計算、PSBT への署名）にとどめる。

## 4. 主な設計判断

### 4.1 使用済みの追跡と「使える分」の表示

- **方法**: フルブロック型のソースは、各ブロックの全 tx を見ている。tx の入力が指す出力（outpoint）が、自分の検出済み出力と一致すれば「使用済み」。追加の暗号処理は要らない。
- **インデックス型（tweak index）では判定できない**（入力を見ていない）。したがって:
  - 使用済みの追跡はフルブロック型のストアだけが行う。
  - 「未使用の合計」に入れるのは、フルブロック由来の検出だけ。インデックス由来の検出は「サーバの申告（未確認）」として別枠に表示し、合計しない。監査（`audit`）で一致しても格上げはしない（D-042 のまま）。
- **reorg**: 使用済みの記録も、検出と同じくブロックに結び付けて保存し、巻き戻しで元に戻す。
- **未承認（mempool）の tx は扱わない**（最初の版）。承認済みのブロックだけを見る。自分が送った直後の出力は、ブロックに入るまで「送金中」として手元の記録で区別する。
- **表示の語**: 「残高」を無条件には使わない。提案: `未使用（自分のノードで確認、N 承認以上）` のように、根拠と条件を必ず添える。
- **SDK への影響**: `SyncStore` に使用済みの記録を足す（ストアのスキーマが変わる）。この機会に O-019（呼び出しをまたぐ巻き戻しの上限）に必要な「最高到達点」も一緒に入れられる。

### 4.2 出力ごとの tweak の受け渡し（D-039 の変更。人間レビュー対象）

出力を使うには、その出力の tweak が要る（支出鍵 = spend 秘密鍵 + tweak）。tweak だけでは資金は動かせないが、**「どの出力がこのウォレットのものか」を結び付ける情報**なので、漏れるとプライバシーを失う。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（推奨）保存しない** | 使うときに、その出力の tx をノードから取り直してスキャンし直し、tweak を得る。メモリ上だけで使い、署名が済んだら捨てる | ディスクに秘密が増えない。ストアは今のまま「鍵素材なし」と言える | 支出のたびにノードへの問い合わせが要る（送金にはどのみちノードが要る） |
| B 保存する | スキャン時に tweak をストアへ保存（上流の実装はこの形） | 速い。オフラインで PSBT を作れる | ストアのファイルが漏れると、受信履歴に加えて結び付けの情報も漏れる。暗号化するなら鍵管理が要る |

- どちらでも、`silent-sync` の既定の公開 API からは tweak に届かないままにする。新しい feature（仮: `spend`）を有効にしたときだけ、ウォレット用の狭い関数が使える形にする。
- A の場合に SDK へ足すもの: 「この出力（txid:vout）の tweak を、フルブロック型のソースから再計算する」関数。結果は `Debug` で表示されない型で返す。

### 4.3 鍵（spend 秘密鍵・シード）の扱い

現状は公開テスト鍵をコードに埋め込んでいる。ウォレットでは本物の（ただし無価値のコインの）鍵を扱う。

| 段階 | 提案 |
|---|---|
| regtest | 起動時に鍵を受け取る（環境変数または標準入力）。ファイルには保存しない。テストは使い捨ての鍵を生成する |
| signet | 上と同じ形で始める。保存が必要になったら、**別の設計案**を出す（OS のキーストアを使うか、パスフレーズで暗号化したファイルにするか。後者は暗号の自作にならないよう、既存の実装と依存の追加が要る） |

- 導出（BIP32、`m/352'/1'/0'/…`）は `bitcoin` クレートの関数を使う。上流のウォレットと同じ経路にする。
- 鍵を持つ型は `Debug` を伏せ字にし、メモリ上の寿命を短くする（今の `ReceiverKeys` と同じ方針）。

### 4.4 送金

- **範囲（最初の版）**: 自分の未使用出力（フルブロック型で確認済みのもの）を入力に、サイレントペイメントのアドレスまたは通常のアドレスへ送る。お釣りはラベル 0（BIP352 の決まり）の自分のアドレスへ。
- **組み立てと署名**: 送金先の出力は上流 `bdk_sp::send` の関数で計算する。署名は上流の PSBT 署名（`send::psbt::sign`）か `bitcoin` クレートの taproot 署名を呼ぶ。どちらを使うかは、実装前に実コードを読んで決め、`docs/RESEARCH.md` に記録する。
- **コイン選択と手数料**: 最小限（手動選択か「古い順」、手数料率は利用者が指定）。凝った選択アルゴリズムは作らない。
- **送信**: いまのノード接続は REST（読み取り専用）。tx の送信には RPC が要る見込み（実装前に確認する: UNVERIFIED）。RPC を使う場合、**認証情報（cookie）の扱い**が規約 3 の新しい対象になる: ファイルから読み、表示・保存しない。接続先はループバックだけ。
- **安全装置**: 送信前に必ず内容（送り先、金額、手数料、お釣り）を表示して確認を求める。`--yes` のような省略は付けない（最初の版）。手数料が金額に対して異常に大きいときは拒否する。

## 5. 段階とゲート

各段階の終わりに、いままでと同じこと（テスト、無効化チェック、独立レビュー、`PROGRESS.md` の報告）を行う。**次の段階には、所有者の了承を得てから進む。**

| 段階 | 内容 | 資金に触れるか | ゲート |
|---|---|---|---|
| W0 | この設計案の承認、CLAUDE.md の規約の改訂 | いいえ | 所有者の承認 |
| W1 | 使用済みの追跡（受信専用のまま）。ストアのスキーマ変更。「未使用（確認済み）」の表示 | いいえ | regtest で、受信 → 外部のウォレットで使用 → 「使用済み」になる。reorg で元に戻る |
| W2 | 鍵の受け取りと導出。tweak の受け渡し（§4.2） | いいえ（署名しない） | 鍵・tweak が出力・ログ・ファイルのどこにも現れないことのテスト |
| W3 | 送金（regtest のみ） | **はい（無価値のコイン）** | regtest で、受信 → 自分で送金 → 相手側で検出。お釣りを自分で検出。独立レビュー |
| W4 | signet | はい（無価値のコイン） | 実際の signet で受信と送金。所要時間の計測 |
| W5 | UI の形を決めて作る | — | 所有者と相談 |

mainnet 対応は、この計画のどこにも含まれない。

## 6. やらないこと（最初の版）

- mainnet、実資金。
- 未承認 tx（mempool）の追跡、手数料の引き上げ（RBF / CPFP）。
- ハードウェアウォレット、マルチシグ、複数アカウント。
- リモートのサーバ（ループバック以外）への接続。
- 鍵のファイル保存（別の設計案が承認されるまで）。
- 上流スキャナのマッチングの変更（O-011 / O-018）。
