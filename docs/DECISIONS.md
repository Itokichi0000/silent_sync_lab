# DECISIONS — 設計上の決定と未決事項

> **名称変更（2026-11-21、D-039）**: `sync-core` → `silent-sync`、`lab-storage` → `silent-sync-sqlite`、`LabNetwork` → `Network`、`LabAddress` → `SilentPaymentAddress`。D-038 までの記述は当時の名前のまま。

各決定には根拠と、見直す条件を書く。`承認` は人間（リポジトリ所有者）の明示的な回答があったもの。

## 決定済み

### D-001 リポジトリ直下をワークスペースにする
設計書 §13 は「新規ディレクトリ `silent-sync-lab` を作る（既存 repo は破壊しない）」。作業対象の `silent_sync_lab` リポジトリが空で用意されていたため、入れ子にせずその直下を Cargo ワークスペースにした。

### D-002 最小構成は `sync-core` + `lab-cli` の 2 crate
`lab-storage` / `lab-bench` は Phase 3 / 5 で実体ができてから切り出す（設計書 §7 の「小さな Workspace から始めてよい」）。依存方向は `lab-cli → sync-core` のみ。`sync-core` は表示・CLI・ストレージに依存しない。

### D-003 `bdk_sp` は git の commit SHA で固定する
`bb373e566fa2a9ee037cb15de2cbe6e679aac7b0`（master HEAD、2026-10-27）。crates.io / タグの 0.2.0 は `K_MAX` 対応（PR #75）より前なので使えない。
- 限界: 未リリースの commit であり、上流が履歴を書き換えるとビルド不能になる。
- 見直し: `K_MAX` を含むリリース（0.3.0 など）が出たら crates.io 版へ移行する。

### D-004 暗号スタックのバージョンを上流の `Cargo.lock` に合わせる
`bitcoin 0.32.7`, `secp256k1 0.29.1`, `secp256k1-sys 0.10.1`, `bitcoin_hashes 0.14.0`, `bech32 0.11.0`, `bitcoin-io 0.1.3`, `bitcoin-units 0.1.2`, `base58ck 0.1.0`, `hex-conservative 0.2.1`, `bitcoin-internals 0.3.0`。
- 理由: 何も指定しないと cargo は `bitcoin 0.32.102` / `secp256k1 0.29.100`（2026 年の「ブリッジ」リリース。後者は 2026-10-26 公開）を選ぶ。上流スキャナ自身のテストが走った組み合わせで動かす方が、実験用の暗号コードとしては保守的。
- 代償: `bitcoin 0.32.8〜0.32.10` の修正（P2P メッセージのデコード、`CompactSize` 範囲チェック等）を含まない。本プロジェクトは P2P を使わないが、Phase 2 で Core からブロックをデコードする際に再評価する。
- 強制方法: `Cargo.lock` を追跡し、CI は `--locked`。

### D-005 K_max 超過時は BIP352 準拠の結果に補正する【承認】
上流は 2324 件以上マッチする tx でエラーを返す（RESEARCH U-1）。BIP352 は最初の 2323 件を検出して停止する。
- 実装（`protocol.rs` `scan_tx_capped_at_k_max`）: 上流が `ScanLimitExceeded` を返したときだけ、(1) 上流の `compute_tweak_data` で公開 tweak を得る、(2) 上流の `get_spks_from_tweak(tweak, K_MAX)` で `k = 2323` の候補 script を得る、(3) tx のコピー上でその script を持つ出力を空にする（位置は保つので vout は不変）、(4) **無改変の上流スキャナ**をもう一度かける、(5) txid を元の値に戻す。結果が 2323 件でなければエラー。
- 独自の曲線演算・ハッシュ・マッチングは書いていない。鍵に触れるのは上流関数だけ。
- 検証: 公式ベクトル #27 で 2323 件。さらに別経路（`get_spks_from_tweak` を `k = 0..2322` で直接呼ぶ）の script 集合と完全一致し、唯一マッチしなかった出力が `k = 2323` の script であることをテストで確認。
- 追加検証: 公式ベクトルは 1 件しか無く形が単純（ラベル 0 のみ、超過 1 件）なので、自作ケース `k_max_cap_with_mixed_labels_reverse_order_and_several_outputs_beyond_the_limit`（無ラベル / ラベル 0 / ラベル 7 を混在、`k` の逆順に配置、無関係な出力と不正な x-only の P2TR を混入、上限超過 3 件）でも vout・金額・ラベルまで一致を確認。独立レビューでも別の 3 ケースで確認済み。
- 代償: 該当 tx では上流スキャンが 2 回走る（デバッグビルドで 50〜100 秒）。攻撃者がこれを起こすには受取人宛の出力を 2324 個以上持つ tx を採掘させる必要がある。
- 見直し: 上流が BIP どおりに直したら、この関数を削除する。

### D-006 「SegWit v>1 を使う tx はスキャンしない」を `sync-core` で補う【承認】
上流に無い規則（RESEARCH U-2）。`ReceiveScanner::eligibility` が prevout の `scriptPubKey` の witness version を見て `SkipReason::SpendsUnknownSegwitVersion` を返す。暗号処理ではなく script の検査。公式ベクトルに該当ケースが無いので fixture（高さ 6）で検証し、「上流単体ならマッチする」ことも同じテストで示している。

### D-007 入力数と prevout 数の不一致はエラー
上流は黙って切り詰める（RESEARCH U-3）。切り詰められると共有秘密が変わり、**支払いを静かに見逃す**。`ProtocolError::PrevoutCountMismatch` を返し、エンジンは範囲全体を失敗にする。

### D-008 上流の panic をエラーとして封じ込める
ソース由来のデータはこの crate ではコンセンサス検証されない。不正な witness で上流がスライス範囲外 panic を起こす（RESEARCH U-5）ので、上流呼び出しを `catch_unwind` で包み `ProtocolError::UpstreamPanic` にする。プロセスを落とさず、その範囲を「スキャン済み」にもせず失敗させる。
- 注意: `panic = "abort"` でビルドすると効かない。ワークスペースでは設定していない。

### D-009 mainnet は型で表現できないようにする
`LabNetwork` は `Regtest` / `Signet` の 2 値のみ。`FromStr`・`serde`・`bitcoin::Network` からの変換のすべてで mainnet を専用エラーで拒否する。`ChainIdentity::verified` は genesis hash も照合するので、「regtest と名乗る mainnet データ」も拒否される。CLI は clap の値パーサ経由で同じ関数を使う。
- `ChainIdentity` のフィールドは非公開で、デシリアライズも `verified` を経由する（レビュー指摘: 公開フィールド + 派生 `Deserialize` だと、mainnet の genesis を持つ値を作れた）。
- アドレスは自前の `LabAddress` で返す。上流の `SilentPaymentCode` は `network` が公開・可変で、呼び出し側が mainnet に書き換えて `sp1…` を出力できたため、外に出さない（レビュー指摘）。公開鍵は取り出せるので、利用者が上流の型を自分で組み立てることまでは防げないし、防ぐ対象でもない。
- 限界: カスタム signet はデフォルト signet と genesis を共有するため、genesis hash だけでは区別できない。

### D-010 固定テスト鍵は BIP352 公式ベクトルの公開鍵素材を使う
`lab-cli` の受取人は `fixtures/bip352/send_and_receive_test_vectors.json` の先頭ケースの鍵。リポジトリ独自の秘密鍵は 1 つも追加していない。
- scan 秘密鍵は `ReceiverKeys` の中に閉じ、`Debug` は伏せ字、`Serialize` / `Display` は実装しない。
- **spend 秘密鍵は読み込まない。** 同じベクトルの送信側に載っている spend 公開鍵を使う（レビュー指摘で変更。以前は秘密鍵を読んで公開鍵に変換していた）。
- ベクトルファイル全体を `include_str!` でバイナリに埋め込んでいるため、バイナリには公開済みのテスト鍵が文字列として含まれる。
- 公開済みの値であっても CLI はこれを出力しない（テストで検査）。
- fixture の送信者鍵は固定文字列のハッシュから導出する使い捨ての値で、どのチェーンの資金も支配しない。

### D-011 検出結果に tweak を持たせない
上流の `SpOut` は出力ごとの tweak を含むが、受信専用の MVP には不要。`DetectedOutput` に入れず、エンジンで捨てる。
- `scan_tx` の戻り値も上流の `SpOut` ではなく自前の `ScanMatch` にした。`SpOut` は（`serde` feature により）tweak ごと直列化できてしまうため（レビュー指摘）。`ScanMatch` は `Serialize` を実装せず、`Debug` は伏せ字、tweak は `sensitive_output_tweak()` という名前のメソッドでのみ取り出せる（公式ベクトルとの照合用）。`ScanReport` の JSON / `Debug` に scan 鍵・tweak が現れないことをテストで検査。
- 見直し: 将来「支出」を扱うなら、保存方法を別途設計し人間レビューを通す。

### D-012 `Evidence` は列挙型にし、tweak 方式を今は作らない
フルブロック方式と tweak 方式を同じ型に押し込めない（設計書 §4.2）。現状は `Evidence::FullBlock` のみで `#[non_exhaustive]`。tweak 方式は Phase 4 で最初の実バックエンドと一緒に追加する。先回りのモックは置かない。

### D-013 fixture は本物のブロック構造を持たせる
合成の「ブロックハッシュ文字列」ではなく、コンセンサス直列化したブロック（有効な regtest PoW、マークルルート、BIP141 witness commitment、BIP34 高さ）を使う。Bitcoin Core が返すデータと同じ形なので、Phase 2 のアダプタと `Evidence::FullBlock` を共有できる。
- witness commitment を検証する理由: BIP352 の入力判定は witness（P2WPKH の公開鍵、Taproot の control block）を読むが、ヘッダのマークルルートは witness にコミットしない。
- **commitment は自前で厳密に照合する。** `rust-bitcoin` の `check_witness_commitment` は witness を全部剥がしたブロックを通してしまう（RESEARCH §3.5）。「commitment があれば必ず一致」「witness があるのに commitment が無ければ拒否」とした。再計算には `rust-bitcoin` の `witness_root` / `compute_witness_commitment` を使う。
- PoW は「ヘッダ自身の `bits` に対して」検証するが、その `bits` が正規の符号化で、ネットワークの上限（regtest / signet）より易しくないことも検査する。これが無いとファイル側が任意の目標値を選べる（レビュー指摘）。最多仕事量チェーンであることは依然として何も言えない。
- 検証しないもの: 署名・script・金額・prevout の実在。`SourceCapabilities::consensus_validated = false` として明示。

### D-014 Phase 1 のエンジンは `scan_range`（ステートレス）
永続化・再開・reorg は Phase 3。CLI のコマンド名は設計書どおり `sync` だが、実行時に「stateless, nothing is persisted」と表示する。エンジンはソースを信用せず、バッチの件数・高さの連続・ハッシュ連結を自分でも検査する。tx 単位のエラーは範囲全体の失敗にする。
- ブロックの中身についても、ソースの申告と無関係に成り立つ事実を検査する: tx が 1 件以上ある／coinbase はちょうど 1 件で先頭／同じ txid が範囲内に 2 度現れない（レビュー指摘: 空の tx リストを返すソースが「8 ブロック走査済み」になっていた）。
- エンジンに検出できないもの: 整合したブロックから非 coinbase の tx を 1 件抜かれた場合。マークルルートを検証するソースか、別ソースとの照合が必要。

### D-015 依存の最適化プロファイル
`[profile.dev.package."*"] opt-level = 3`。K_max ベクトルは約 540 万回の点演算を要し、無最適化では数分かかる（上流の slow テストは 124 秒）。

### D-016 BIP34 の高さは自前で読む
`bitcoin::Block::bip34_block_height` は高さ 1〜16（Bitcoin Core が `OP_1`〜`OP_16` で符号化する）を読めない。regtest は必ずここから始まるので `source::coinbase_height` を用意した。script の解析のみ。

### D-017 witness の無い SegWit 入力はエラーにする
P2WPKH / P2WSH / P2TR、および P2SH で包んだ P2WPKH / P2WSH（scriptSig がちょうど 1 つの v0 witness program の push）を使う入力の witness が空なら `ProtocolError::MissingWitness`。
- 経緯: 独立レビューが発見し、再現を確認した不具合。witness を剥がしたブロック（witness フラグなしで取得したブロックなど）を fixture アダプタが受理し、上流がその入力を「適格でない」として黙って無視するため、**検出が 7 件から 0 件になってもエラーにならなかった**。
- 根拠: コンセンサス上、これらの出力は空の witness では使えない（BIP141 / BIP341）。したがって正しいチェーンデータで誤ってエラーになることはない。pay-to-anchor など他の witness program は対象外（空の witness で使える）。
- script の検査のみで、暗号処理は増やしていない。tx が自分に関係あるかどうかに関係なく検査する（剥がされたデータは BIP352 に使えないため）。
- D-013 の厳密な commitment 照合と二重になっているのは意図的。commitment を確認できないソース（将来の tweak 方式など）でもスキャナ側で止まる。

### D-018 独立レビューと「検査の無効化チェック」を各フェーズで行う
Phase 1 の実装後、文脈を共有しない別エージェントに敵対的レビューを依頼した。確認済みバグ 1 件（D-017）、堅牢化 7 件、「壊してもテストが落ちない検査」9 件の指摘を受けた。バグは自分のテストで再現してから修正し、他はコードの読解または無効化チェックで確認して対応した（未対応は O-010, O-011, O-012 に記録）。
- 再発防止として `scripts/mutation_check.py` を追加。検証コードの各検査を 1 つずつ無効化し、いずれかのテストが落ちることを確認する（現在 27 件、生存 0。`docs/logs/phase1_mutation_check.log`）。
- 検査を追加・変更したら、このスクリプトの項目も同時に更新する。

### D-019 Bitcoin Core は 32.1 を使う
所有者の回答が無かったため、「Oracle v2 と同一ノードで比較できること（30 以上）」と「現行の最新安定版」を満たす 32.1 を選んだ。`scripts/fetch_bitcoind.sh` がバージョンと SHA-256 を固定し、`VERIFY_SIGNATURES=1` で `SHA256SUMS` の署名も検証する（既定の必要数 3、実測 8 件有効）。バイナリはリポジトリに含めない。
- 見直し: 別バージョンで検証したい場合はスクリプトの `VERSION` / `TARBALL_SHA256` を更新し、E2E を再実行する。

### D-020 Core バックエンドは REST のみを使い、認証情報を扱わない
`sync-core` の `CoreRestSource` は `-rest=1` の REST（`chaininfo` / `blockhashbyheight` / `block` / `spenttxouts` / `headers`）だけを読む。
- 理由: (1) RPC cookie やパスワードをアダプタが一切持たない（設計書 §5.7, §5.8）。(2) ブロックも prevout もバイナリで取れ、金額の浮動小数表記を避けられる。(3) BlindBit Oracle v2 と同じ取得経路なので、Phase 4 の比較条件を揃えやすい。
- 代償: REST は認証なしなので、同じホストの他プロセスも読める。対象は公開チェーンデータのみ。Bitcoin Core 30 以上が必要（`spenttxouts`）。
- **ループバック限定**: URL は `http://` かつ `127.0.0.1` / `::1` / `localhost` のみ。それ以外はリクエストを 1 つも送らずに拒否する。リモートノードは範囲外。
- **mainnet 拒否**: `chaininfo` の `chain` が `main` なら専用エラー。さらに高さ 0 のハッシュをネットワークの genesis と照合する（「regtest」と名乗る別チェーンを拒否）。`tip()` のたびにチェーン名を再確認する。
- ノードが検証済みのデータでも、アダプタは再検査する: 要求したハッシュとの一致、マークルルート、witness commitment（厳密）、PoW、BIP34 高さ、取得範囲内の連結、prevout の件数、余剰バイト。witness なしで返されたブロックはここで落ちる。
- scan 鍵はリクエストに含まれない。送るのは高さとブロックハッシュだけ。
- `core-rest` は cargo feature（既定で無効）。有効にすると HTTP クライアント `minreq`（TLS・プロキシ機能なし）が入る。

### D-021 テスト専用クレート `lab-testkit`
fixture 生成器、regtest ノードの起動 / 停止、テスト用 tx の署名と SP 出力の導出、偽 REST サーバをここに集めた。**上流の送信関数と署名処理を使うのはこのクレートだけ**で、`sync-core` と `lab-cli` の通常の依存には入らない（両者の `dev-dependencies` のみ）。
- 以前は `#[path]` で各テストに取り込んでいたが、Phase 2 以降は複数クレートのテストから使うため独立させた。
- ワークスペースの `unwrap_used` 拒否はこのクレートには適用しない（テスト補助は失敗時に panic するのが正しい）。

### D-022 実ノードを使う E2E は `#[ignore]` とし、専用 CI ジョブで実行する
`BITCOIND_EXE` が必要なテスト（`regtest_e2e.rs`, `regtest_cli.rs`）は通常の `cargo test` では `ignored` と表示される。`-- --ignored` で実行し、`BITCOIND_EXE` が無ければ**失敗する**（黙って通過しない）。CI では `regtest-e2e` ジョブがバイナリを取得・検証して実行する（設計書 §11）。
- E2E の tx は実際に署名し、1 件は mempool 経由でブロードキャスト、残りは `generateblock` でブロックに入れる（SegWit v2 を使う tx など、ポリシー上リレーされないものを載せるため。コンセンサス検証は通っている）。
- mainnet 拒否の E2E は、**ネットワークに一切接続しない** mainnet パラメータのノード（`-connect=0 -dnsseed=0 -listen=0`、genesis のみ）で行う。

### D-023 偽 REST サーバで「嘘をつくノード」を通常テストに含める
`lab-testkit::fake_core_rest` が fixture チェーンを Bitcoin Core の REST と同じ形で配信する。応答を差し替えられるので、bitcoind なしで Core アダプタの拒否動作（witness を剥がしたブロック、別のブロック、余剰バイト、prevout の不足、mainnet を名乗るノードなど）を検査できる。fixture アダプタと Core アダプタが同じチェーンで**同一の結果**になることもここで確認している。

### D-024 永続化は「ストアの抽象 + SQLite 実装」に分ける
`sync-core` は `SyncStore` トレイトと、全実装が守るべき不変条件 `check_append` を定義するだけで、データベースに依存しない。SQLite 実装は `lab-storage`（`rusqlite`、SQLite 同梱ビルド）。メモリ実装 `MemoryStore` は参照実装兼テスト用。
- 同じ振る舞いテスト群（`lab-testkit::sync_suite`）を両実装に適用する。SQLite だけの性質（再オープン後の永続、上書き拒否、スキーマ版、ファイル権限、失敗時のロールバック、ファイル内に鍵が無いこと）は `lab-storage` 側で別途テスト。
- ストアに入るもの: 紐付け情報、走査済みブロックのハッシュ連鎖、検出した出力。**鍵・tweak は入らない**（テストでファイルのバイト列まで検査）。
- 検出した出力は受信履歴なので、ファイルは作成時に所有者のみ読み書き可（0600）にする。
- 追記とロールバックはそれぞれ 1 トランザクション。`synchronous = FULL`。

### D-025 ストアは「何に紐付いているか」を持ち、食い違えば何もしない
`StoreMeta` = チェーン（ネットワーク + genesis）、ウォレット ID（公開鍵 2 つから導出した公開の識別子）、バックエンド ID、ラベル集合、birthday とその根拠、スキャナ版。`sync` は毎回これを照合し、1 つでも違えば `BindingMismatch` でストアに触れずに終了する。
- **ラベル集合は後から変えられない。** 走査済みのブロックは新しいラベルで調べていないため、足すと「同期済みに見えるが見逃している」状態になる。変える場合は新しいストアで再スキャンする。
- バックエンドを混ぜない。比較は別々のストアで行う。
- スキャナ版が違うストアは再スキャンを要求する（検出ロジックが変わった可能性があるため）。
- **birthday とその根拠は必須。** birthday より前の入金は決して見つからないので、CLI は `--birthday` と `--birthday-basis` の両方を要求し、根拠をストアに記録して `status` に表示する（設計書 §6）。

### D-026 reorg は「分岐点まで巻き戻して再スキャン」、遅れているだけのソースは拒否
`sync` 開始時にチェックポイントのハッシュをソースと照合する。一致しなければ、保存済みブロックを高さの降順にたどって分岐点を探し、それより上のブロックと検出を 1 トランザクションで削除してから再スキャンする。削除した検出は `ReorgReport` に載せる。
- **ソースの tip がチェックポイントより低く、かつその tip が保存済みブロックと一致する場合は reorg とみなさず、エラーにする**（`SourceBehindCheckpoint`）。再起動直後や同期中のノードを reorg と誤認して走査済みの結果を捨てないため。実ノードの `invalidateblock` 直後もこの状態になり、より長い競合チェーンが現れた時点で reorg として処理される（E2E で確認）。
- チャンクの先頭ブロックが保存済みチェックポイントに連結しない場合（tip の確認とブロック取得の間にチェーンが動いた）は `ChainMovedDuringSync` で中断。ストア側の不変条件も同じ入力を拒否する（二重の防御）。
- 分岐点が birthday より下なら、birthday から再スキャンする。
- 巻き戻しの深さの上限は、当初は設けていなかった。後に D-041 で追加（既定 100 ブロック）。

### D-027 中断耐性は「チャンク単位のコミット」で得る
`sync` はチャンク（既定 100 ブロック）ごとに「取得 → 検査 → スキャン → ストアへ 1 トランザクションで追記」を行う。どこで止まっても、ストアは最後にコミットしたチャンクの状態で、次回の `sync` がそこから続ける。
- 検証: 全チャンクサイズ × 全停止位置での再開、ソース障害、コミット失敗の注入、そして **CLI プロセスを SIGKILL して再開**（`killed_sync_resumes_without_loss_or_duplicates`）。いずれも最終結果が一括同期と一致し、重複なし。
- `--chunk-delay-ms`（非表示オプション）はチャンク間に待ちを入れるだけで、強制終了のテストとデモ用。エンジン側にフックは入れていない（CLI が 1 チャンクずつ `sync` を呼ぶ）。

### D-028 CLI: ステートレスな実行は `scan`、永続同期は `sync`
Phase 1〜2 の `sync`（何も保存しない）を `scan` に改名し、`sync` はストアを使う本来の意味にした。`lab init` / `status` / `received list` を追加。既定のストアは `./silent-sync-lab.sqlite3`（`*.sqlite3` は `.gitignore` 済み）。
- 鍵はストアに保存しない。CLI は固定のテスト鍵を毎回読み込む（D-010）。

### D-030 tweak インデックス型の証拠と、そのスキャン方法【人間レビュー対象】
`Evidence::TweakIndex` を追加した。中身は tx ごとの「公開 tweak データ（`input_hash·A`）」と「Taproot 出力（vout・金額・出力鍵）」で、**入力は含まない**。フルブロック型と同じ型には押し込めていない（設計書 §4.2）。
- スキャンは `ReceiveScanner::scan_indexed_tx`。共有秘密の計算は上流の `compute_shared_secret`、出力のマッチングは上流の `scan_txouts` を、インデックスが挙げた出力だけを持つ代用トランザクションに対して呼ぶ。K_max の補正は D-005 と同じ方法。**独自の曲線演算・ハッシュ・マッチングは書いていない。**
- 公式ベクトルのうち公開 tweak データが定義される受信ケース（スキャン対象外でないもの）すべてで、この経路の結果がフル tx 経路と一致することを確認（K_max ベクトルを含む）。スキャン対象外のケースには tweak が無く、この経路で比べるものが無い。
- この経路では BIP352 の適格性規則（入力が必要）を適用できない。どの tx をスキャン対象とするか、tweak が正しいか、tx が実在するかは、インデックスの申告に従うしかない。
- 「暗号処理に関わる変更」に当たるため、所有者のレビューを求める（設計書 §12）。実装前の質問は行わず、D-005 と同じ「上流関数だけで構成する」方針の延長として進めた。

### D-031 Oracle バックエンドは「自分のノードのヘッダ + Oracle の tweak インデックス」
`BlindbitHttpSource` は BlindBit Oracle v2 の HTTP JSON（`/info`, `/full-block/<h>`）を読む。ブロックの同一性（高さ・ハッシュ・親）は、利用者自身のノード（`CoreRestSource`、D-029 のとおり genesis から検証済み）から取る。
- Oracle が返すブロックハッシュは、ヘッダ源の同じ高さのハッシュと一致しなければエラー。これにより「別チェーンのインデックス」「追いついていない Oracle」「範囲外に HTTP 200・空ハッシュを返す挙動（RESEARCH §4.1 B-1）」が「入金なし」に化けない。
- Oracle のネットワーク名が `main` / `mainnet` なら拒否。ヘッダ源のネットワークと違っても拒否。`tweaks_only` 構成（出力を配らない）も拒否。
- ループバック限定（D-029 と同じ HTTP クライアント）。ホスト型の Oracle への接続は範囲外で、実装していない。接続するなら IP・時刻・要求範囲が相手に見える（設計書 §5.4）。
- **インデックスの中身は検証できない。** tx の省略、誤った tweak、存在しない入金の捏造は、このバックエンド単体では検出できない（`SourceCapabilities` はすべて `false`）。テストで実演している。
- gRPC は使っていない。上流は HTTP の JSON ブロック系エンドポイントを deprecated としているため、将来消えれば gRPC への移行が必要（O-014）。
- リクエストに含まれるのは高さだけ。scan 鍵・アドレス・ラベルは送らない。

### D-032 ローカルで計算する tweak インデックス（`LocalTweakIndex`）
フルブロックのソースを包み、インデックスサーバが軽量クライアントに渡すのと同じ形の証拠を、手元で計算して返す。**サーバの模型であり、第三者からは何も取得しない。** 同一チェーンで 2 種類の証拠を比較でき、オフラインで動き、故障注入の土台になる（設計書 Phase 4 の「fixture ベースの `indexed_data` アダプタ」）。
- `IndexPolicy::Bip352` は BIP352 がスキャン対象とする tx だけを載せる。`IgnoreSegwitVersionRule` は SegWit v2 以上を使う tx も載せる（BlindBit Oracle v2 で観測した挙動の再現用）。

### D-033 `verify`（cross-check）の意味と終了コード
同じ範囲・同じ鍵で候補と参照の 2 つのソースをスキャンし、片方だけが検出した出力ごとに、手元の証拠から言える最も具体的な理由を付ける（参照が BIP352 上スキャン対象外と判定／参照のブロックに tx が無い／候補が tx を省略／tweak が違う／出力を省略／出力の内容が違う／ブロックハッシュが違う／説明できない）。

- CLI は差異があれば終了コード 4 を返す（スクリプトから検出できるように）。

### D-041 reorg の巻き戻し深さに上限を設ける（O-013 を解決）

`SyncOptions::max_reorg_depth`（既定 `Some(100)`、`None` で無制限）を足した。保存済みのチェックポイントがソースのチェーンに無いとき、**捨てることになるスキャン済みブロックの数**がこの値を超えるなら `SyncError::ReorgTooDeep` で拒否し、ストアには一切触れない。

- 既定の 100 は、Bitcoin が coinbase の使用を認める深さ。それより深い書き換えは、本物の reorg よりも「ソースの異常か嘘」である可能性のほうがはるかに高い。本当に起きたのなら、利用者が上限を上げて（CLI は `--max-reorg-depth <n>` または `none`）やり直せる。
- 上限は**分岐点を探しながら**検査する。探し終えてから比べるのではないので、ソースは上限より深くストアを辿らせることができない。このためエラーが伝える深さは「少なくとも `at_least` ブロック」（常に上限 + 1）で、実際の分岐の深さではない。
- birthday より下まで食い違う場合（保存分すべてを捨てる）も、保存分のブロック数として数える。
- 「ソースが単に遅れている」場合（`SourceBehindCheckpoint`）は従来どおり reorg として扱わない。
- **【D-044 で訂正】上限は 1 回の呼び出しに対するもので、呼び出しをまたぐ合計には効かない。** 当初の文面（「超える要求は拒否する」）は言い過ぎだった。あわせて、チェックポイントより**短い**競合チェーンには追随しないことにした（`CompetingChainShorter`）。詳細は D-044。
- 故障注入マトリクスには行を足していない（マトリクスは「まっさらなスキャン」に対する故障の表で、同期済みのストアを前提にしない）。挙動は同期スイート（`reorgs_deeper_than_the_limit_are_refused`、MemoryStore と SQLite の両方）と CLI のテストで固定した。

### D-042 保存済みの検出結果を参照ソースで監査する（O-017 を解決）

`audit_store(reference, scanner, store, options)`（当初は `wallet_id` を別引数で受けていた。D-044 でスキャナから導出する形に変更） を足した。ストアが持つ範囲（birthday〜チェックポイント、または指定した一部）を参照ソースでスキャンし直し、**ストアの中身**と 1 ブロック・1 出力ずつ比べる。ストアは読むだけで、変更しない。CLI は `silent-sync audit --db <store> --backend core ...`（差分があれば終了コード 4、`verify` と同じ）。

- **なぜ必要か。** `cross_check`（`verify`）は 2 つのソースに「いま」問い合わせて比べるだけなので、同期した時だけ嘘をつき、後は正直に答えるサーバを見つけられない（FAULT_INJECTION I19）。ストアに残っているのは嘘をつかれた時点の結果なので、それを自分のノードと比べれば分かる。
- **報告する差分。** ストアに無い出力（`store_omitted_output`）、ストアだけにある出力（参照ブロックから理由を特定: tx が無い／BIP352 上スキャン対象でない／スキャンしたが不一致）、金額またはラベルの相違、ブロックハッシュの相違（ストアが別のチェーンに乗っている高さ）。
- **ストアの束縛。** チェーン・ウォレット・ラベル集合・スキャナのバージョンは一致が必須（`sync` と同じ検査を共有）。**バックエンドは違ってよい**（インデックスで埋めたストアを自分のノードで監査するのが主な用途）。
- **エラーにするもの**（「差分なし」と報告しない）: 何も保存されていない、範囲が保存範囲の外、参照が範囲を出せない・不整合なバッチを返す、ストアが自分の不変条件に反している（保存ブロックの欠落、保存ブロックと食い違う検出）。
- **限界。**
  - 監査の価値は参照と同じ。自分のノード（フルブロック型）が参照のときだけ、チェーンそのものに基づく結果になる。参照がインデックスの場合はレポートと CLI がそう明記する。
  - 「ストアに無い」理由は区別できない（ソースが省いたのか、ストアが書き換えられたのか）。スキャン時に受け取った証拠はストアに残していない。
  - ストアが持たない高さについては何も言わない。最新ブロックを隠すソース（F06）は監査では分からない。
  - 監査で一致しても、保存済みの検出の証拠種別（`tweak_index`）は書き換えない。「監査済み」という状態をストアに記録する機能は作っていない（必要になれば別途設計する）。
- 故障注入マトリクスに「結果を保存したストアの監査」の列を足した。I19 の判定は「単独でも後の突き合わせでも分からないが、ストアの監査で分かる」に変わり、3 つの方法のどれでも分からない故障は現在の表には無い。
- 型は `verify` の `Difference` / `Explanation` / `Side` を共用する（`Side::Candidate` がストア側）。`Explanation` に `StoreOmittedOutput` を追加した。

### D-043 ラベルを後から追加する: 範囲をもう一度スキャンして、別のストアに作り直す（O-006 を解決）

ストアはスキャンに使ったラベル集合に束縛されている。スキャン済みのブロックは他のラベルについて調べておらず、未知のラベル宛ての出力は同じ tx の後続の出力も隠すので、ラベルを足すには**範囲全体のスキャンをやり直す**しかない（tx ごとの共有秘密を保存しておけば省けるが、それは秘密を保存することになるのでやらない）。

- **`rescan_into(source, scanner, current, fresh, options)`**: 使用中のストア `current` は読むだけ。空のストア `fresh` を `current` と同じ束縛（チェーン・ウォレット・バックエンド・birthday とその根拠）に新しいラベル集合で初期化し、birthday からスキャンする。`Ok` を返すのは、`fresh` が `current` の代わりになれるときだけ:
  1. `fresh` が `current` のチェックポイント以上まで進んでいる（足りなければ `Incomplete`。同じ引数でもう一度呼べば続きから再開する）
  2. `current` のチェックポイントのブロックが `fresh` のチェーンに含まれている（含まれなければ `CheckpointNotOnChain`。`current` が reorg に追随していない）
  3. `current` が持つ検出が、すべて `fresh` にそのまま（ブロック・金額・ラベル・出所まで同じ形で）ある（無ければ `NotReproduced`）
- **差し替えは呼び出し側が行う。** こうすると、どの時点で失敗・中断しても使用中のストアは一切変わらない。`SyncStore` トレイトに「束縛を書き換える」操作を足す必要も無い。SQLite には `replace_store_file(current, fresh)` を用意した。1 回の rename で差し替え（クラッシュしても旧か新のどちらか）、取り消せない操作なので**自分でも**「同じ束縛・ラベルは増える方向だけ・チェックポイントを含む・検出を 1 件も失わない」を検査してから実行する。
- **ラベルは追加だけ。** ラベルを減らす・入れ替える再スキャンは `LabelsRemoved` で拒否する（そのラベルで見つけた出力が消える）。同じラベル集合での再スキャン（作り直し）は許す。別バージョンのスキャナが書いたストアを作り直す用途にも使える。
- **バックエンドは同じでなければならない。** 別のバックエンドで作り直すと、「前の結果を再現できたか」の比較が、ソースの違いと区別できなくなる。
- `NotReproduced` は、同じソースでラベルが増えるだけなら**通常は**起きない（検出は増える方向にしか変わらない）。起きたら差し替えずにエラーにし、該当する検出を返す。**【D-044 で訂正】「本来起きない」は誤りだった。** BIP352 の手順に従わない tx（同じ出力カウンタ `k` で受信者の 2 つのアドレスに払うもの）では、ラベルを知ると検出される出力が**入れ替わる**（上流スキャナは `k` ごとに 1 出力しか報告しない。O-011）。受信者のアドレスを 2 つ知っている者なら誰でもそういう tx を作れるので、これは「そのラベルの追加を妨害できる」ことを意味する（O-018）。
- CLI: `silent-sync lab add-label --db <store> --label <m> ...`。再スキャン先はストアの隣の `<store>.rescan`。中断したら残し、次の実行で続きから。完了したら検査のうえ差し替える。別の再スキャンの残りがあるときは、`--restart` を案内して止まる（勝手に消さない）。同じラベルのままスキャンし直す `lab rescan` もある（別バージョンのスキャナが書いたストア用。D-044）。
- **変わらないこと**: ラベルのバックアップは引き続き必要（復元時にラベルを知らなければ、その宛先への入金は見つからない）。再スキャンの費用は birthday からの全範囲で、チェーンが長いほど高い。

### D-047 使用済み出力の追跡（W1）

- **方法**: フルブロック型の証拠は、ブロックの全 tx とその入力を含む。入力が指す出力（outpoint）が検出済み出力なら「使用済み」として、使った tx とそのブロックを記録する。暗号処理は増えない。同じブロック内で作られて使われた出力、同じチャンク内の後のブロックで使われた出力も拾う。
- **インデックス型では記録しない**（入力が見えない）。その場合「使用済みの記録が無い」は「未使用」ではなく「不明」。ウォレットは、フルブロック由来の検出だけを未使用の集計に入れる。
- **ストア**: `SyncStore::append` に `spends` を足し、ブロック・検出・使用済みを 1 回で原子的に記録する（別々に書くと、途中で落ちたときに「スキャン済みなのに使用済みが抜けている」状態が残る）。`SyncStore::spends()` を追加。巻き戻しは、消えるブロックに記録された使用済みも取り消す（`ReorgReport::spends_reverted` で報告）。共通ルール `check_append` に、使用済みの検査（検出済みの出力であること、追加中のブロックにあること、作られたブロックより前でないこと、2 回使われていないこと、自分自身に使われていないこと）を足した。
- **SQLite**: スキーマ版を 2 に上げ、`spent_outputs` 表を追加。版 1 のファイルは開かない（「何が使われたか」の情報が無いので、空の表を足すだけの移行は「何も使われていない」という嘘になる。新しく作って同期し直す）。開くときの検査に、宙に浮いた使用済みの記録の検出を追加。
- **監査**: 参照がフルブロック型のとき、ストアがフルブロックで検出した出力について、使用済みの記録も突き合わせる（`spend_differences`）。参照がインデックスのときは比較せず、レポートにそう書く（`spends_compared: false`）。
- **再スキャン**: 作り直したストアが、元のストアの使用済みの記録をすべて再現していなければ差し替えない（`SpendsNotReproduced`。使用済みの出力が未使用に見えるようになるため）。`replace_store_file` も同じ検査をする。
- **扱わないもの**: 未承認の tx（mempool）。ブロックに入るまでは使用済みにならない。

### D-048 ウォレットの実装（W2・W3）で決めたこと

- **tweak の受け渡し**: `silent-sync` の feature `spend`（既定で無効）に `spend::recover_spendable(source, scanner, detection)` を置いた。検出のブロックをフルブロック型のソースから取り直し、tx をスキャンし直して、出力と tweak を「表示されない型」（`SpendableOutput`）で返す。検出とソースの両方がフルブロック由来で、ブロック・tx・出力・金額・ラベルがすべて検出時と一致するときだけ成功する。既定の構成からこのモジュールに届かないことは `probes/` で検査する。
- **署名の方法**: 上流の PSBT 署名（`sign_sp`）は使わず、同じ計算を `secp256k1` / `bitcoin` の関数を直接呼んで行う（理由と確認内容は RESEARCH §3.6）。自前の式は書いていない。鍵に触れる呼び出しは `silent-wallet/src/send.rs` だけにある。
- **鍵と走査器を 1 つの型に**: `Wallet::new(keys, network, labels)` が走査器を作る。「署名する鍵」と「スキャンする鍵」が食い違う組み合わせを作れない（SDK 側で `wallet_id` をスキャナから導出するようにした D-044 と同じ考え方）。
- **コイン選択と手数料**: 候補を渡された順（CLI は古い順）に、支払いと手数料を賄えるまで取る。手数料は「署名後の仮想サイズ × 指定の率」。お釣りが中継される最小額（P2TR で 330 sat）に満たないときは、お釣りを作らず手数料に含める。上限（手数料率 500 sat/vB、手数料合計 100,000 sat、入力 200 個）を超えるものは作らない。
- **出力の並び**: 支払いを渡された順に、最後にお釣り（ラベル 0）。プライバシーへの配慮はしていない（THREAT_MODEL §4.6）。
- **送信**: Bitcoin Core の REST は読み取り専用なので、`sendrawtransaction` は JSON-RPC で行う（`rpc.rs`）。ループバックの IPv4 のみ、認証は cookie ファイル。送信前に `testmempoolaccept` で受理されることを確かめる。
- **未承認の間の扱い**: 送った tx の入力は `<store>.pending.json`（txid と outpoint だけ。鍵素材なし）に記録し、「未使用」から外す。同期でその入力の使用済みが記録されたら消す。別の tx に使われていたら「承認され得ない」として消す。
- **CLI**: シードは環境変数 `SILENT_WALLET_SEED`。作成・表示のコマンドは無い。`send` は内容を表示して `SEND` の入力を待つ（省略不可）。`--no-broadcast` は署名済み tx を表示するだけ。ストアは自分のノード（フルブロック型）にだけ束縛できる。
- **signet（W4）**: この環境からは signet のピアに接続できず、**BLOCKED**。コードは `--network signet` を受け付けるが、signet での動作は UNVERIFIED。
- **UI（W5）**: 未着手。形は所有者と決める。
