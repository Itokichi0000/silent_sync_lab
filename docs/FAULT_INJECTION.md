# 故障注入の結果（Phase 5、設計書 T10〜T12）

EXPERIMENTAL — NOT FOR MAINNET OR REAL FUNDS.

バックエンドが**受け取るデータ**に不正を注入し、実際のアダプタとエンジンがどう振る舞うかを観察した結果。
「検出できる不正」と「検出できない不正」を分けて示すことが目的で、後者を隠さない。

- 表は `cargo run -p lab-testkit --bin fault_report` の出力そのもの。テスト
  `crates/sync-core/tests/fault_matrix.rs` が、各行の判定と、この文書の表が生成結果と一致することを検査する
  （コードの挙動が変わると、このファイルを更新しない限りテストが失敗する）。
- 対象チェーンは決定的 fixture（8 ブロック、ラベル 1 を知るウォレットに 7 出力）。
- 注入箇所: 偽の Bitcoin Core REST サーバの応答、偽の BlindBit Oracle の応答（ヘッダは正直な偽ノードから取る）、
  ソースがエンジンに渡すバッチ。

## 見方

- **Faulty source alone**: 不正なソースだけを使ってスキャンした結果。
  `scan fails` は範囲全体が失敗し、何も「スキャン済み」と報告されないこと（fail-closed）。
  **`scan succeeds`** は、誤った結果が成功として報告されたこと。
- **Cross-check**: 同じ範囲を、正直なフルブロック型ソース（自分のノードに相当）と `verify` で突き合わせた結果。
- **Verdict**:
  - `refused (fail-closed)`: 単独で検出できる。
  - `no effect`: 結果は正しいまま。
  - `NOT detected alone; shown by a cross-check`: **単独では検出できない**。正直なフルブロック型ソースとの突き合わせで初めて分かる。
  - `NOT detected`: 突き合わせても分からない（今回の表には該当なし。ただし下の「この表が示さないこと」を参照）。

## 読み取れること

1. **フルブロック型（自分のノード）は、ブロックがコミットしている内容の改変をすべて単独で拒否する**（F01〜F04、F07〜F11）。
   ヘッダ鎖・PoW・merkle root・witness commitment・件数の検査による。
2. **フルブロック型でも単独で検出できないものが 2 つある。**
   - F05: スキャン範囲より前に作られた prevout を偽られると、入金を黙って見逃す。prevout は何にもコミットされていないため、原理的に検査できない。
     自分のノードはコンセンサス検証済みのデータを返すので、これは「ノードを信用する」という前提そのもの。
   - F06: 最新ブロックを隠すノードは「短いチェーン」と区別できない。報告された先端までの結果は正しいが、その先の入金は見えない。
3. **tweak インデックス型は、省略・改変・捏造をどれも単独では検出できない**（I01〜I06）。
   - 省略（I01〜I03、I05）: 入金を黙って見逃す。設計書 §5.5 のとおり。
   - **金額の改変（I04）: 誤った金額のまま「検出」として報告される。**
   - **捏造（I06）: 存在しない入金が「検出」として報告される。** インデックスの項目（txid・vout・金額・出力鍵）は、ヘッダにコミットされたブロック内容と結び付けられていない。
     捏造には受信者宛ての正しい出力鍵が要るため、作れるのは実在の支払いの項目を知っている者（インデックスサーバ自身、または送信者と結託したサーバ）に限られるが、ウォレット側では区別できない。
   - したがって **tweak インデックス由来の検出は「サーバがそう言った」以上の意味を持たない**。検出結果には証拠の種類（`tweak_index`）を必ず付けており、フルブロック由来の検出と同じ確度として扱ってはならない。
4. **インデックス型でも、ブロックの同一性に関わる不正は拒否する**（I11〜I15）。ブロックの高さとハッシュは自分のノードのヘッダから取り、Oracle の申告と一致しなければ失敗にする。Oracle が遅れている・停止している場合も「空のブロック」とは扱わない。
5. **応答の構造の乱れ（順序違い・重複・欠落・部分応答）はすべて拒否する**（B01〜B04、I07、I08）。
6. 順序の入れ替え（I09）と、自分宛てでない項目の省略（I10）は結果に影響しない。I10 は「このウォレットにとっては」無害というだけで、サーバが正直である証拠にはならない。

## 永続同期での挙動（同期スイートで検査）

| 事象 | 挙動 | テスト |
|---|---|---|
| reorg（T09） | 分岐点まで巻き戻し、消した検出を報告して再スキャン | `reorg_rolls_back_and_rescans`、実ノード `persistent_sync_follows_a_real_reorg` |
| 巻き戻し後・コミット後の障害（T12） | `Interrupted` として、変更済みの内容（巻き戻し・コミット済みチャンク）を報告。再実行で続きから | `a_failure_after_a_reorg_rollback_still_reports_the_reorg`、`source_outage_leaves_a_resumable_store`、CLI `an_interrupted_sync_reports_what_it_changed` |
| ソースがチェックポイントより手前にいる（T12） | 拒否。保存済みの結果を捨てない | `a_source_behind_the_checkpoint_is_refused` |
| 先端取得とブロック取得の間にチェーンが動いた | 拒否（`ChainMovedDuringSync`）または `tip_changed` として報告。「同期済み」とは言わない | `blocks_that_do_not_extend_the_checkpoint_are_refused`、`the_reason_a_sync_stopped_is_reported` |
| 再送された項目が別チャンクに入る（I07 の永続版） | ストアの不変条件「同じ出力は 1 度だけ」で拒否 | `a_replayed_index_entry_is_refused_by_the_store_across_chunks` |
| 応答が返ってこない（タイムアウト） | 失敗（既定 30 秒） | `a_silent_server_times_out` |
| プロセスの強制終了（SIGKILL） | 直前のコミットまでが残り、再開で漏れ・重複なし | CLI `killed_sync_resumes_without_loss_or_duplicates` |

## この表が示さないこと（限界）

- **突き合わせ（cross-check）は、参照側が正直で完全であることを前提にしている。** 参照も同じ嘘をつけば差分は出ない。
  自分で運用していない 2 つのサーバの一致は、独立した正しさの証明にならない（設計書 §5.6）。
- 「範囲より前の prevout の嘘」（F05）は、参照側のノードが同じ嘘をつく場合は検出できない。表の F05 が「突き合わせで分かる」になっているのは、参照が正直な別ソースだからである。
- ここで注入したのは 31 種類の不正だけで、網羅ではない。特に、時間的な攻撃（応答を遅らせて古い先端を見せ続ける等）、リソース枯渇、
  複数の不正の組み合わせは扱っていない。
- 対象は 8 ブロックの fixture。規模に依存する不具合（チャンク境界など）は `crates/sync-core/tests/long_chain.rs` で別に検査している。
- リモートのサーバに対するプライバシー上の露出（IP アドレス、接続時刻、要求範囲）は故障注入の対象外。`docs/THREAT_MODEL.md` を参照。
