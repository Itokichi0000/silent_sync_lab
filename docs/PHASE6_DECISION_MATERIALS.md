## 2. 測定と実装から分かった事実

判断に効きそうなものだけを挙げる。数値の出典は `BENCHMARK_REPORT.md`、不正の扱いは `FAULT_INJECTION.md`。

### 2.1 性能

- ループバック・小さなブロックでは、**Oracle 経由は Core 直結より速くならなかった**（1000 ブロックで wall 1.07 倍）。クライアントの CPU は 0.58 倍、受信バイトは 0.82 倍。
- この条件では時間の大半が HTTP の往復で、BIP352 の計算ではない。**インデックス方式の利点が出るはずの条件（mainnet 規模のブロック、インターネット越し）は測っていない。**
- Core 直結は、接続のたびに genesis からのヘッダ鎖を取り直す（チェーン長に比例。O-016）。
- 永続化の費用は小さい（1000 ブロックで scan との差は誤差の範囲）。再開は残りの分だけの時間で済む。

### 2.2 信頼と完全性

- **フルブロック型は、接続先が自分のノードである限り、ノードの示すヘッダ鎖と食い違う内容をすべて単独で拒否できる。** 検出できないのは「範囲より前の prevout の嘘」「先端を隠すこと」「ヘッダごと一貫した別チェーン」で、いずれも自分のノードを信用する前提に含まれる。接続先が自分のノードであること自体は検証していない（regtest / signet では PoW が根拠にならない）。
- **tweak インデックス型は、省略・改変・捏造をどれも単独では検出できない。** 入金の見逃しだけでなく、**誤った金額の検出**と**存在しない入金の検出**が成功として返る。捏造は受信者のアドレスを知っていれば作れる。
- 検出できるようにする唯一の手段は、信頼できるフルブロック型ソースとの突き合わせで、それが出来るならインデックスは要らない、という構造になっている。
- 自分で運用していない複数サーバの一致は、独立した正しさの証明にならない。
- 突き合わせ（`verify`）は両ソースに再度問い合わせて比べる。スキャン時だけ嘘をついたサーバは見つからない（保存済みの結果との照合は未実装。O-017）。

### 2.3 上流とエコシステム

- 上流 `bdk_sp` は実験的と自称しており、BIP352 正本との差異を 2 点確認した（K_max、SegWit v>1。RESEARCH U-1 / U-2）。**未報告**（O-002）。
- BlindBit Oracle は、BIP352 がスキャン対象外とする tx（SegWit v2 の出力を使うもの）の tweak も配る（RESEARCH B-2）。**未報告**。準拠したクライアントは、これをサーバ側の差異として扱う必要がある。
- BlindBit Oracle の HTTP JSON は上流で deprecated（O-014）。gRPC は未実装。
- 「未知のラベルが同じ tx の後続の出力を隠す」という BIP352 の性質により、ラベル集合はウォレットの復元に必須の情報になる（O-006）。

### 2.4 実装してみて分かったこと

- 仕様の落とし穴は暗号そのものより、**その周辺**に多かった: witness を落としたブロックでもハッシュは変わらない、prevout は何にもコミットされていない、チェーン名は申告にすぎない、reorg と「遅れているだけ」の区別、エラーの前に行った変更の報告、2 実装間の並び順。
- 独立レビュー（各フェーズ 1 回、計 4 回）は、毎回、自分のテストでは見つけられなかった欠陥を見つけた。Phase 1: witness 除去の受理。Phase 2: genesis への連結未確認。Phase 3: 巻き戻しが報告されない経路。Phase 4: ヘッダ上限なし、障害時のキャッシュ破棄。
- 検査を 1 つずつ外してテストが落ちるか確かめる方法（無効化チェック、現在 147 項目）は、「あるだけで試されていない検査」を継続的に見つけた。

## 3. 3 つの進路と、それぞれに効く材料

設計書 §14 の評価基準に沿って整理する。**需要に関する行は、この実験からは何も言えない**（利用者や開発者への聞き取りをしていない）。

| 判断材料（§14） | SDK へ寄せる | ウォレットへ寄せる | インフラ研究へ寄せる |
|---|---|---|---|
| 再利用の需要 | **UNVERIFIED**（聞き取りなし） | **UNVERIFIED** | **UNVERIFIED**。ただし未解決の課題は実在する（2.2） |
| 技術成果 | 同期コアは分離済みで、ストア・ソースはトレイト。ただし **API は安定させていない**（フェーズごとに変えた）。鍵管理は無い | 同期状況・巻き戻し・証拠種別を報告する型はある。**UI・鍵管理・支出・残高は無い**（非目標だった） | 故障注入の枠組み、突き合わせ、差分の説明、上流 2 実装の逸脱の発見 |
| メンテ負担 | API 互換性、上流 `bdk_sp` への追従（rev 固定・補正 2 点）、ドキュメント | 上に加えて UI、鍵の保護、実資金の責任、サポート | ノードとインデックスサーバの運用、計測環境 |
| 最大の差別化 | fail-closed の徹底と、証拠の種類を型で区別する設計 | 「何が検証済みで何がサーバの申告か」を利用者に見せること | 「インデックス型で何が検出できないか」の実証と、その緩和策の研究 |

### 3.1 SDK 化に進む場合に必要なもの（現状との差）

- 公開 API の整理と安定化方針（現状は実験の都合で公開している項目が多い）。
- 鍵の受け渡しの設計（現状は公開テスト鍵の埋め込み）。scan 鍵をどこに置き、どう渡すか。
- ヘッダ鎖の永続化（O-016）、reorg 深さの上限（O-013）、ラベル追加時の再スキャン（O-006）。
- 非同期 I/O の要否、signet / mainnet の扱い（**mainnet は現在、型で拒否している**。外すのは人間レビュー必須の変更）。
- 上流への報告と、補正を外せる時期の見極め（O-002）。
- ライセンスの決定（O-001）。**現状ライセンスが無いので、第三者は利用できない。**

### 3.2 実験ウォレットに進む場合に必要なもの

- 上のすべてに加えて: 鍵管理、支出（署名）、未使用残高の追跡、UI。**いずれも本実験の非目標で、何も無い。**
- 「検出は残高ではない」という現在の線引きを、どこまで動かすか。
- インデックス型を使う場合、誤った金額・存在しない入金が表示され得ること（2.2）を、利用者にどう見せるか。これは UX の問題であると同時に安全性の問題になる。

### 3.3 研究・インフラに進む場合の候補

- インデックスの完全性を検証可能にする方法（ブロックにコミットされたデータとの結び付け、フィルタとの併用、サンプリング検査など）。**本実験では手を付けていない。**
- mainnet 規模・インターネット越しでの計測（本実験で測れていない条件そのもの）。
- 上流 2 実装の逸脱の報告と修正への協力。
- gRPC インターフェースでの再計測、Oracle の他の構成（cut-through、dust フィルタ）。

## 4. 決める前に所有者が答える必要のある問い

1. **ライセンス**（O-001）。どの進路でも最初に必要。
2. **上流への報告**（O-002）。bdk-sp の 2 点と BlindBit Oracle の 1 点を、issue / PR として出すか。
3. **誰のための成果物か**。開発者（SDK）、利用者（ウォレット）、研究コミュニティ（計測と検証）のどれを最初の読者にするか。この実験は需要を調べていない。
4. **mainnet を扱う意思があるか**。あるなら、鍵管理・監査・責任の範囲を先に決める必要がある。無いなら、SDK / 研究の範囲に留まる。
5. **インデックスサーバを信頼の前提に置くか**。置くなら、2.2 の限界を受け入れる設計になる。置かないなら、自分のノードが要る利用者に限られる。
6. **人間レビュー対象の承認**（D-005、D-006、D-030）。上流の挙動を補正している 3 箇所。

## 5. 実装者の所見（事実ではなく意見）

以下は Claude の意見であり、判断材料の一つとして読んでほしい。

- この実験で最も「他に無い」と感じたのは、**証拠の種類ごとに、何が検証されていて何がサーバの申告にすぎないかを、型・表示・テストで一貫して区別したこと**と、それを故障注入で裏付けたことである。速度の優位は示せていない。
- したがって、次の一歩として最も根拠があるのは、**範囲を絞った SDK 化（受信側の同期と検証のみ、regtest / signet のまま）と、測れていない条件での計測・上流への報告を並行させること**だと考える。
  ウォレット化は、非目標だった領域（鍵・支出・UI）をすべて新規に作ることになり、この実験の成果が効く範囲が相対的に小さい。
- ただし、これは需要の裏付けを欠いた意見である。設計書 §14 の第 1 行（再利用の需要）を確かめる手段をこの実験は持っていなかった。
- どの進路でも、**mainnet を拒否する型上の制約は、鍵管理と監査の方針が決まるまで外さない**ことを勧める。
